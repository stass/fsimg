# APFS driver

## Scope

The [APFS format design](design-apfs.md) establishes the on-disk facts, the
profiles and the evidence gates. This document maps them onto code: the
modules of `lib/formats/apfs/`, the driver state behind the common reader and
writer, the algorithms that keep checkpoint selection, object resolution,
tree traversal, verification, planning and emission bounded, and the tests
that qualify them.

The driver implements the common contracts without exceptions: the
[format descriptor and probe](design-formats.md#format-descriptors-and-profiles),
[prepared directories](design-directories.md),
[logical content](design-content.md) including its zero and held extents,
[emission](design-emission.md), [sizing](design-sizing.md) and the
[POSIX metadata extension](design-metadata.md). Common code gains no
APFS-specific branch. The volume and snapshot read settings reach the driver
through the read options under the capability record's `read_settings`, as
write settings do through `write_settings`.

`object.c` is the only place that interprets an object reference and
`btree.c` the only place that interprets a node, so header, checksum,
storage-class, range, ordering and height checks exist once. The writer
packs nodes with the same arithmetic in `btree.c` that the reader's
validation states, so a node the writer emits is one the reader's rules
accept.

The driver also needs three facilities shared beyond it:

* `lib/core/crc32c.c`: CRC-32C, tested against its published check value.
* Unicode tables in `lib/core/`: canonical decomposition with canonical
  combining classes and case folding, generated by the Ruby generator that
  produces the FAT tables, from the Unicode Character Database at the
  version E4 establishes, with its Unicode-3.0 notice, and tested against
  `NormalizationTest.txt`.
* `lib/codec/`: the imported LZFSE and LZVN decoders behind the
  [codec design's](design-codecs.md#imported-lzfse-and-lzvn-decoders)
  interface.

## Codecs

Every APFS integer is little-endian and decoded with the shared
[scalar codecs](design-binary-primitives.md) after its span is proved; the
big-endian resource-fork header of a compressed file is decoded in
`compress.c`, the one place that reads big-endian fields.
Decoded records are C structures with `_t` typedefs holding validated
values only:

| Type | Fields |
| --- | --- |
| `apfs_obj_t` | checksum, OID, XID, kind, storage class, flags, subtype |
| `apfs_nx_t` | block size, block count, the three feature masks, UUID, next OID and XID, both area descriptions and this checkpoint's runs, space manager, object map and reaper OIDs, maximum volume count, volume OID array |
| `apfs_cpm_t` | kind, subtype, byte size, volume OID, ephemeral OID, address |
| `apfs_omap_t` | flags, snapshot count, tree type and OID, snapshot tree type and OID, most recent snapshot |
| `apfs_node_t` | node flags, level, key count, the four locations, and for a root the footer |
| `apfs_vol_t` | index, the three feature masks, flags, role, UUID, name, tree types and OIDs, counts, group UUID, integrity and sealed-tree OIDs |
| `apfs_inode_t` | inode number, parent, private ID, four times, internal and BSD flags, count, owner, group, mode, uncompressed size, decoded extended fields |
| `apfs_drec_t` | parent, name span, stored hash and length, child, add time, type, sibling ID |
| `apfs_extent_t` | private ID, logical offset, length, physical block, flags, crypto ID |

Encoding is the exact inverse and writes every reserved byte as zero, so an
emitted object contains no unspecified byte. The Fletcher-64 function is
tested against blocks captured in E1 before any fixture is read.

## Open

`open` runs a fixed sequence; each step validates everything it uses before
the next starts:

1. **Block 0.** One read of 4096 bytes, then `B` bytes once the block size is
   known. Geometry, features and areas as the format design states.
2. **Checkpoint.** `checkpoint.c` reads the descriptor ring once with one
   block window, recording each valid superblock as an `(XID, slot)`
   candidate in a charged stream. Candidates are examined from the largest
   XID down by rereading only their descriptor runs; the first whose run is
   whole is selected, and a larger one whose run is not sets `clean` to
   false. Its mappings are copied into a paged array in metadata scratch and
   sorted by OID, and each mapped object is then read once and checked; a
   failure is `FSIMG_ECORRUPT`, with no fallback to an older checkpoint.
   Selection costs the `D` descriptor blocks, each candidate's run, and one
   data run.
3. **Space manager.** The ephemeral object is read through the mapping
   table; its main-device free count gives `free_bytes`.
4. **Container object map.** The physical object and its tree root.
5. **Volume.** Each nonzero slot of the volume array is counted; the
   selected slot, or the only one, is resolved at the checkpoint XID through
   the container map, and its superblock validated, including features and
   the refusal tables. A missing or ambiguous selection fails here.
6. **Volume object map.** The live volume object map, a physical object
   checked against the checkpoint XID.
7. **Snapshot.** With `snapshot=`, the snapshot tree is searched for the
   name record, the metadata record is read, and the snapshot's volume
   superblock replaces the live one, under the header rule E9 fixes; the
   lookup XID for the volume's virtual objects becomes the snapshot's.
8. **Volume trees.** The filesystem tree root is resolved through the live
   volume object map at the lookup XID; in the sealed profile, the integrity
   object and the sealed file-extent tree root are read too.
9. **Root.** Inodes 2 and 3 are looked up and must be directories with
   parent 1.
10. **Information.** The volume information and its details are filled from
    the decoded objects.

`reader->content_domain` is `[B, N * B)`, the container without block 0.
APFS has no separate data region, so the domain does little beyond bounding
content to the container; ownership verification is what detects a file
extent that names metadata.

## Objects

`apfs_object_read(reader, ref, window)` takes a reference
`(storage class, OID, XID, kind, subtype, map)` and a window of `B` bytes:

* physical: the OID is the block, which must lie in `[1, N)`;
* virtual: `omap.c` resolves the OID at the reference's XID through the
  named map's cursor, and the object's XID must equal the found key's;
* ephemeral: binary search of the paged mapping array.

It reads the block with one exact read, verifies the checksum, and checks
kind, subtype, storage class, OID and XID. An object larger than one block
is read only where the format design allows one, the space manager, through
a charged buffer of its mapped size, which the format design ties to the
size the geometry implies for its structure and address array. A failure
names the object's role, never its bytes.

## B-trees

A cursor belongs to one tree: its root reference, storage class, comparator
and record codec. It holds the current root-to-leaf path, one window and one
table-of-contents position per level, plus the separator bounds each level
was entered under. Windows are allocated as the path deepens and kept for the
session; a tree of height `h` holds at most `h` windows, and the format
design bounds `h` by 16.

`btree.c` offers three operations:

* `seek(cursor, key, mode)`: position on the last record at or below the
  key, or the first at or above it. The search starts from the deepest
  level whose separator bounds contain the key, so consecutive nearby seeks
  read only the nodes that change; otherwise it descends from the root,
  validating each node as it is loaded.
* `next(cursor)`: advance to the following record, climbing and descending
  as needed; the bounds of every node entered are checked against its
  parent's separators.
* `record(cursor)`: borrow the current key and value spans, valid until the
  cursor next moves.

Node validation is the format design's list, run once per load. A repeated
node on the current path is a cycle, `FSIMG_ECORRUPT`. Each node load
charges one work unit and its read. A seek is bounded by the height. A scan
visits each node once: every node's keys must lie within the separator
range its parent gives it, and the ranges of a parent's children are
disjoint and increasing, so a node referenced from two places, or a
subtree repeated under two separators, fails the range check before its
records are used, and a scan is bounded by the tree's distinct nodes.

The reader keeps these cursors: the container object map (open only), the
volume object map, a filesystem lookup cursor for inode and attribute
lookups, a filesystem scan cursor for directory records, a content cursor for
file extents, and, in the sealed profile, the sealed file-extent tree.
Verification adds its own scan cursors. Because every cursor's windows are
charged when first needed, a small tree costs one window.

The packing arithmetic decides, for a node of a given kind and level, how
many records of given encoded lengths fit: the table of contents grows by
one entry per record, keys and values are 8-byte aligned unless the tree is
unaligned, and a root reserves its 40-byte footer. The writer uses it to fill
nodes and the verifier to check the writer's own output in tests.

## Names and keys

`names.c` validates a name and derives its comparison form by the volume's
rule: case folding then canonical decomposition with canonical reordering,
decomposition alone, or the bytes. The form is produced as code points into a
bounded buffer: the generator asserts the largest expansion of any code point,
and the buffer holds that expansion of a 1022-byte name. The hash is CRC-32C
over the code points as the format design defines. The namespace key is the
form as UTF-8, at most three times the name's bytes, which the generator also
asserts; the common key buffer, `FSIMG_DIRECTORY_KEY_BYTES`, therefore holds
4096 bytes, enough for the longest name an APFS record can hold.

`key` converts a selection query component with the same function after
checking it is valid UTF-8 without slash or NUL; an invalid component is
`FSIMG_EINVAL`. The `ambiguous` text describes two APFS names that the
volume treats as equal, without quoting them, as the common contract
requires.

## Directories

`prepare` takes inode 2 at level 0 and otherwise the current entry's inode,
which `replay` proved is a directory. It seeks the scan cursor to the first
directory record of that inode and iterates while the owner and kind match.
For each record it checks the key variant, the name rules, the stored length
and hash, and the value: the child inode at least 16 (or in the volume-group
space) and a type in the format design's table. It admits the child with a
17-byte payload: the child inode (u64), the record type (u8) and the sibling
ID or zero (u64), little-endian. Admission charges the entry; the walker's
key sort then rejects equivalent names. A device or socket type fails the
directory's preparation with `FSIMG_EUNSUPPORTED` naming the entry, as the
metadata contract requires.

`replay` re-validates the payload, looks the child inode up through the
lookup cursor, validates it, and checks its mode type against the record
type. A directory child's recorded parent must be the directory that holds
its record, and its name extended field must equal the record's name; these
are the driver's cycle and sharing rules, which need no claimed-object set
because a cycle would give a directory two parents and a second record
would give it a second name. The entry snapshot is then built:

| Kind | Size | Content state |
| --- | --- | --- |
| File | Data-stream size, or the compression header's size | Private ID and size; or the compression state below |
| Symbolic link | Target length | The target, read from its attribute into a 1024-byte held buffer |
| Directory, FIFO | Zero | None |

For a compressed file, `replay` reads the `com.apple.decmpfs` attribute,
validates its header against the inode, and records the codec, the
uncompressed size and either the inline payload's location or the resource
fork's data-stream reference. `reader->initialized` is the entry's size.
Inode lookups at replay are random tree descents; their cost is measured by
the scale tests, and a wide directory whose lookups dominate is the trigger
for sorting a directory's child inodes once per preparation instead.

## Content

`resolve` answers an offset `o` of the current file with one extent:

* **Uncompressed file.** The content cursor seeks the last file-extent
  record of the private ID at or below `o`. If the record covers `o`, the
  result is a mapped extent over its blocks, or a zero extent when its
  physical block is zero. If it ends at or before `o`, the next record must
  not exist, and the result is a zero extent to the size; otherwise the gap
  is `FSIMG_ECORRUPT`. Sequential reads continue with `next`, which checks
  that each record starts where the previous one ended, so a forward read
  validates the whole tiling once and needs no descent per extent.
* **Symbolic link.** One held extent over the target bytes.
* **Compressed file.** Chunk `c = o / 65536` is decoded into a 64 KiB held
  buffer, unless it is the chunk already held, and the result is a held
  extent over that chunk clipped to the size. The compressed chunk is read
  into a second buffer bounded by the chunk table's entry, which must not
  exceed the codec's worst-case expansion of 64 KiB.

Mapped extents are checked against `[1, N)` before they are returned;
delivery then clips them to the request and the initialized length and reads
only inside the content domain. A held buffer is valid until the next
`resolve` or advance, as the content design requires.

## Verification

`verify.c` runs once over the container and once through the common walker.

**Container pass.** It re-reads the selected checkpoint's descriptor and data
runs, the space manager, the reaper and the container object map, and appends
claims `(first block, count, class, owner)` to a claim stream: block 0 and
the two areas as fixed claims; the internal pool as one range; every node of
every object map; every live object version each object map maps, at its
size, tombstones excluded; every physical tree node; the reaper's list
objects; every free-queue entry; and the space manager's chunk-information,
address and bitmap blocks that lie outside the internal pool. Those inside
the pool are checked against the pool's own bitmap as sub-allocations,
never claimed twice. For each volume it scans the object map, the
extent-reference tree, the snapshot tree with each snapshot's
extent-reference tree, and the filesystem tree with dedicated cursors; the
filesystem scan appends a data claim for every mapped file extent, owner
`(volume, private ID)`, and the extent-reference scans append a reference
record for every physical extent.

**Record reconciliation.** The filesystem scan visits each object's records
together because they share the owner prefix, so most checks are local and
need no storage: the inode record (kind 3) is followed by its attributes
(4), sibling links (5), the data-stream ID (6) and extents (8) of a stream
whose private ID is the inode number, and, for a directory, its directory
records (9), whose count must equal the child count; extents tile their
stream; attributes and extended fields are well formed; counts by kind
accumulate for the superblock. Facts that join different owners go to streams that are sorted
once:

* name references `(child, parent, type)`, joined with the inodes in scan
  order to check existence, kind, a directory's single parent and each
  file's link count;
* sibling maps `(sibling ID, inode)`, joined with the sibling links;
* stream uses `(private ID)` from inodes and stream-backed attributes,
  joined with the data-stream ID records' counts;
* runs of directory records sharing a parent and hash longer than one,
  whose comparison forms are sorted to find equivalent names; an adversarial
  run therefore costs a sort, not quadratic comparisons.

**Allocation merge.** The claim stream is sorted by first block. The merge
walks it with `spaceman.c`'s pager, which visits chunk-information blocks in
address order and each chunk's bitmap block in 4 KiB windows. For each block
it checks the format design's rules: metadata claims never overlap any other
claim; data claims overlap only data claims of the same volume, inside one
reference record whose count, checked by a second sort of
`(reference, stream)` pairs, equals the distinct streams sharing it; a block
is allocated exactly when claimed; each chunk's free count and the device's
free count equal the clear bits.

**Walk.** The common walker visits the selected volume once, with payload
read-through when requested, and the report counts its files, directories and
bytes, and the container's allocated and free blocks. A completed
verification sets `FSIMG_VOLUME_FREE` from the counted free blocks. A
refused feature in any volume, or an unknown optional or read-only-compatible
feature bit, makes the report incomplete with `FSIMG_EUNSUPPORTED`; the walk
is never reported complete after skipping an object.

## Writer settings

`validate` accepts the common options with these rules: `sector_bytes` and
`allocation_unit_bytes` zero or 4096; `label` NULL, selecting `Untitled`, or
valid UTF-8 of at most 255 bytes; `fat_root_entries`, `byte_order`,
`inode_capacity`, `reserve_percent` and `mountpoint` at their defaults, which
the common settings check enforces; `volume_uuid` nonzero unless
`FSIMG_WRITE_REPRODUCIBLE` is set; `epoch` at least zero and representable in
nanoseconds; `volume_bytes` zero or a multiple of 4096 of at least the
native minimum container. `volume_serial` is ignored, since the CLI generates
one for every format. The capability record's `write_settings` names
`FSIMG_SETTING_VOLUME_UUID` and `FSIMG_SETTING_CASE_SENSITIVE`, the latter
governing the `case_sensitive` field, CLI `case=insensitive|sensitive`.

## Planning

The plan object embeds `fsimg_plan_t`, the geometry, the volume flags, the
format time, the derived UUIDs, the node counts of each tree, the region
table, and one paged array of rows keyed by catalog ID, row 0 being the root.
A row holds the inode number, the parent's row, the child count, the content
length, the first data block, and the inode fields already encoded under the
metadata policy. Rows, the sorted record stream and the collision stream are
the only per-entry state.

Planning runs a fixed sequence of passes over the frozen catalog:

1. **Entries.** For each catalog ID in order: check the name's length and
   rules; compute its comparison form and hash; append
   `(parent, form, ID)` to the collision stream; assign inode `15 + ID`, the
   root being 2 and the private directory 3, with the private ID equal to the
   inode; count children into the parent's row; validate kind and metadata
   representability under the
   [metadata policy](design-metadata.md#writer-policy); accumulate data
   blocks `ceil(size / 4096)` and `initialized_bytes`. The volume's next
   object identifier is one past the largest inode assigned.
2. **Collisions.** Sort the collision stream; two equal `(parent, form)`
   records fail with `FSIMG_EINVAL` naming both entries.
3. **Records.** Append every filesystem record each entry needs, and the
   native records of the empty volume, to a record stream, encoded in full
   except the physical block of each file extent, which is a fixed-width
   field emission fills from the row. Sort it with the filesystem
   comparator. Encoded lengths depend only on the catalog, so the sorted
   stream is final.
4. **Packing.** Run the packing arithmetic over the sorted stream to count
   the filesystem tree's nodes per level, in the completion order emission
   reproduces: one open node per level, each node closed when the next
   record or separator does not fit, open nodes closed from the leaves up
   when the records end, and a top node that does not fit a root's smaller
   capacity split in two under a new root; count the extent-reference tree's
   nodes from its record count, one per nonempty file, in catalog order; and
   count the object maps' nodes from their fixed-size records: one per
   filesystem node in the volume map, one volume superblock in the container
   map.
5. **Geometry.** With exact `volume_bytes`, `N = volume_bytes / 4096`. With
   automatic sizing, binary search the smallest `N`, in steps of the native
   granularity, for which the fixed regions the native formatter gives for
   `N` (checkpoint areas, internal pool, chunk structures), the metadata
   nodes, the data blocks and the requested free space fit. A binary search
   needs the predicate to be monotone over the step: the fixed regions grow
   by a few blocks per chunk of `32768` blocks in the native containers E1
   and E12 measure, and a test checks the property against those tables, so
   a region where the native layout jumps is found before the search relies
   on it. The maximum volume count follows the native rule for `N`.
6. **Layout.** Assign regions in the format design's order; assign OIDs from
   1024 in a fixed order: the ephemeral OIDs of the space manager, reaper
   and free queues, the volume superblock's virtual OID, then the
   filesystem nodes' virtual OIDs in completion order. The container's next
   OID is one past the last; the volume's next object identifier is one past
   the largest inode. Place each nonempty file's run in catalog order. The
   allocated blocks form the native fixed regions and one contiguous run.
7. **Summary.** Fill `fsimg_plan_info_t` with the volume, metadata,
   allocated, free and initialized bytes, the block size and count. The
   common [loss policy](design-metadata-loss.md) installs the loss count
   after every step succeeds.

Every value derives from the catalog, the options and these rules, so
byte-identical output does not depend on source order, budgets, sort fan-in,
scratch placement, locale or time zone.

## Emission

The common emission object has already zeroed the sink. The driver emits:

1. For each row in ID order: the payload copy for a nonempty file over its
   run.
2. The filesystem tree: the sorted record stream is replayed through the
   packing arithmetic a second time, with each file extent's physical block
   filled from its row. Leaves are written as they fill; one open node per
   level collects separators, so index nodes are written as their children
   complete and the root last, with its footer. Node `k` in completion order
   takes OID `first + k` and block `base + k`, which is what planning
   counted.
3. The volume object map's tree from the node sequence of step 2, the
   extent-reference tree from the rows, the empty snapshot tree, the volume
   object map, the volume superblock, the container object map's tree and
   object.
4. The space manager's bitmaps as runs of ones and zeros, its
   chunk-information and address blocks, the internal pool's bitmap, the
   empty free queues and the reaper in the native form, then the space
   manager itself.
5. The checkpoint mapping block and the container superblock in the
   descriptor area, and the same superblock in block 0.

Every object's checksum is computed as it is written. Every emitted byte
comes from a row, the geometry, the sorted records or a profile constant.

## Resource bounds

| Operation | Work and residency |
| --- | --- |
| Probe and open | Block 0, one pass over the descriptor ring and each candidate's descriptor run, the selected checkpoint's mapped objects, the container and volume map paths, the volume superblocks, the root inodes; the candidate stream and the paged mapping array |
| Listing | Per directory: one scan of its records and the common key sort; per entry: one inode lookup and, for a link or compressed file, one attribute lookup. No file payload is read |
| Content | Per sequential read: one cursor advance per extent; per random offset: one tree descent; per compressed chunk: one decode of at most 64 KiB |
| Verification | One scan of every tree of every volume; the claim, name-reference, sibling-map, stream-use and collision streams, each sorted once; one pass over the chunk structures and bitmaps; one walk of the selected volume |
| Planning | One catalog pass, two external sorts (collisions and records), one packing pass, a bounded binary search, one layout pass |
| Emission | Payload bytes, one replay of the sorted records, and metadata proportional to entries and container size |

Resident state per reader is the geometry, the selected superblocks, the
cursors' windows (at most 16 per cursor), one 1024-byte held buffer, and,
while a compressed file is current, two 64 KiB compression buffers plus the
codec's state: the LZFSE decoder's scratch, about 45 KiB, or zlib's inflate
state through the common allocation adapter. Everything proportional to entries, records or blocks is charged
scratch. Every loop charges the session and observes cancellation.

## Failure classification

The format design's table governs. Within the driver, a failed exact read is
`FSIMG_EIO`; a step that runs out of budget or scratch is `FSIMG_ELIMIT`; a
lookup that misses a required object is `FSIMG_ECORRUPT` naming the object's
role. A codec failure is `FSIMG_ECORRUPT` for malformed input and
`FSIMG_ELIMIT` for exhausted resources, never a silent short read.

## Tests

`test/apfs.c` owns a synthetic container generator written from the format
design with its own offset tables, Fletcher-64, node packing and CRC-32C; it
shares no code with `lib/formats/apfs/`. Its names use a small alphabet whose
comparison forms it computes itself, plus the E4 vectors with their recorded
hashes, so it needs no normalizer of its own. It builds containers in memory
at every legal block size, with chosen checkpoint rings, object maps,
multi-level trees, volumes, records and extents, and mutates them for the
format design's
[acceptance matrix](design-apfs.md#acceptance-and-independent-validation).

`test/apfs-write.c` creates containers through the public API and reads them
back through the reader and verifier and through an independent checker
written from the format design, sharing no code with the driver. It compares
bytes across source order, metadata cache size, scratch placement and time
zone, scans every unused byte, and with `--native` compares an empty
container's structures with the E1 capture of the same size field by field,
apart from UUIDs, times and the formatting identifier.

`test/apfs-integration.sh` runs the oracles the host has and skips the others
explicitly: on macOS, the native captures, `fsck_apfs -n`, `hdiutil attach`
with a manifest comparison, and the write-after-create cycle; on Linux,
`apfsck`, `apfs-fuse` and `fsapfsinfo` on copied images. Native captures come
from a path in the environment and are never redistributed. `fuzz/apfs.c`
feeds the probe, checkpoint selection, object maps, nodes, records, content
and verification under finite budgets, seeded from the generator, with the
generator's checksum repair so mutations reach past the checksums. Fault
tests inject allocation, scratch, short-read, EOF, source-change and
cancellation failures at every stage of reading, planning and emission and
check cleanup. Scale tests grow the container size, one directory's width,
a file's extent count, the tree heights and a file beyond 4 GiB separately,
recording I/O calls, node loads and peak scratch.
